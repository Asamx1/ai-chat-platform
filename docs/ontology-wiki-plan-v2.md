# AI-chat × Ontology × LLM Wiki：统一知识应用方案 v2

日期：2026-09-24。状态：设计方案，尚未实施。方案基于本轮前段对 `E:\AI-Workstation\work\ai-chat-platform\repo` 的代码检查；未重新运行服务或测试。用户已确定集成进 AI-chat，并要求最终阶段将所有功能集成为一个应用。

## 1. 产品目标与边界

将 AI-chat 扩展为个人知识应用：用户提供原始资料，系统持续将其编译成有证据、有语义关系、可查询和可维护的知识网络。日常摄入、阅读、关联浏览、问答、维护、备份均在一个应用中完成。Obsidian 保留为同一份 Markdown Vault 的可选阅读入口。

本方案的 Ontology 指知识工程本体：定义类型、实例、关系、属性、约束以及明确的推理规则。它贯穿摄入、查询和维护。LLM Wiki 负责持久的可读知识页面，本体负责统一知识含义与允许的关系，检索负责寻找证据。

原始约束继续有效：raw 仅由用户添加，AI 只读；wiki 由 AI 维护；CLAUDE.md 与本体规则由用户和助手共同维护；正式概念页至少有两份去重的原始素材；回答不得以模型常识填补证据空白。

## 3. 三层架构与文件组织

维持原有三层逻辑架构。本体定义属于规则层，本体实例与带来源断言属于知识网络层，不另设一个与 Wiki 竞争的数据源。

```text
PersonalWiki/
├── CLAUDE.md                 # 人机共同维护的工作规则
├── AGENTS.md                 # 引导代理读取同一规则
├── schema/                   # 规则层的机器可读附件
│   ├── ontology.yaml         # 类型、属性、关系、标识规范
│   ├── constraints.yaml      # 必填字段、端点类型、来源等检查
│   └── inference-rules.yaml  # 有限的显式推理规则
├── raw/                      # 仅用户添加，AI 只读
│   ├── articles/
│   ├── papers/
│   ├── transcripts/
│   └── assets/
└── wiki/                     # AI 维护的知识网络
    ├── index.md
    ├── log.md
    ├── sources/
    ├── concepts/
    ├── comparisons/
    ├── answers/
    ├── reports/
    └── _meta/
        ├── sources/         # 稳定来源 ID、版本、来源家族、定位映射
        ├── entities/        # 概念候选、实例、别名和状态
        ├── assertions/      # 有证据的原文断言及其状态
        ├── derivations/     # 推理结论与依赖、规则版本
        ├── extracted/       # OCR、字幕解析等派生内容
        └── releases/        # 发布清单、文件哈希与规则版本
```

Vault 放在代码仓库外，以 `WIKI_VAULT_PATH` 配置。最终由应用安装向导选择位置。Windows 和 WSL 通过路径映射访问同一份文件，不维护两份可写副本。

权威数据各有明确职责：Markdown 是知识正文的权威版本；_meta 中的记录是结构化实体和证据的权威版本；schema 是本体规则的权威版本。正文关键陈述绑定 assertion ID。对同一事实的文字表达与结构化表达必须在同一发布批次校验一致，不允许两端独立覆盖。

应用正常生成页面时同时发布相关结构记录。若检测到 Obsidian 人工修改正文，生成待协调修订，完成证据与一致性检查后才更新图谱；不自动把自由文本变成已确认事实，也不静默覆盖人工内容。

## 4. 最小本体设计

### 4.1 四类基础对象

| 对象 | 表达什么 | 设计示例 |
|---|---|---|
| 类型 Class | 对象属于哪种类别 | Concept、Model、Method、Task、Metric、Dataset、Source |
| 实体 Entity | 一个具体对象或被管理的概念 | 某个模型版本、某个数据集、一个检索方法概念 |
| 断言 Assertion | 对某对象的属性或关系的陈述 | 某模型支持某任务、某实验测得某指标 |
| 证据 Evidence | 支持或反驳断言的原始片段 | PDF 某页、Markdown 某节、字幕时间段 |

Claim 不直接等于事实。每条断言记录状态，例如候选、有证据支持、有争议、已被替代、失效。推理结论另记 origin=inferred，不混入原文陈述。模型自报置信度只用于复核排序，不作为事实成立的凭据。

初始采用通用核心本体，再增加 AI 领域词表。模型提出新的类型或关系时进入规则变更建议；新增、删除或改变语义须由用户确认版本。实例和已有关系类型下的证据记录可按既定规则自动维护。

### 4.2 关系需要明确含义

| 关系 | 起点 → 终点 | 使用约束 |
|---|---|---|
| instance_of | 实例 → 类型 | 区分具体模型与模型类别 |
| subclass_of | 类型 → 类型 | 表达类型包含关系，可按已批准规则传递 |
| broader_than | 主题概念 → 主题概念 | 用于主题导航，不自动等同于逻辑子类 |
| uses | 系统/方法 → 技术/方法 | 必须有原文证据，默认不传递 |
| supports_task | 模型/方法 → 任务 | 记录版本和适用条件 |
| evaluated_on | 实验 → 数据集 | 与指标、设置共同表达结果 |
| supports / contradicts | 证据 → 断言 | 关联具体陈述，不把整篇文章标成绝对正确或错误 |
| supersedes | 新版本 → 旧版本 | 记录适用范围和生效条件 |
| related_to | 实体 → 实体 | 弱关联，仅用于导航，不支持事实推理 |

关系定义必须包含方向、允许的端点类型、是否对称、是否传递和必需的上下文。`[[双链]]` 是导航链接；语义关系来自通过检查的结构化记录，不能根据两个页面互相链接就推断“使用”“因果”或“优于”。

### 4.3 每条断言保存的内容

最少字段：稳定 ID、主体、谓词、客体或值、肯定/否定、适用条件、有效时间、状态、证据列表、来源类型（原文/推理）、规则版本和修订版本。数值结果还需保存单位、数据集、测试设置和评价指标；不同条件下的数值不得直接判为矛盾或生成排名。

每条证据包含：sourceId、sourceVersion/hash、原文定位、必要摘录以及支持/反驳关系。原文位置不可可靠提取时降级为明确的章节或摘录定位，不伪造页码。

举例仅说明数据结构，不代表当前库内已有事实：

```text
断言：模型甲 v1 支持任务乙
证据：来源 S1，第 3 节，文件哈希 H1
适用条件：指定输入格式和版本
状态：有来源支持，只有一个独立来源
页面策略：可展示于来源摘要；相关新概念暂不升为正式概念页
```

### 4.4 两篇来源门槛与实体识别

首次出现的新领域概念，只记录候选实体并写入来源摘要；不得通过建立“实体页”绕过正式概念页门槛。两份去重的原始素材实质讨论同一概念后，才发布其概念页。

Source、Claim 等预定义系统类型属于本体规则，不属于依据资料新建的领域概念页。单来源事实可以有证据地回答，但必须保留其来源范围，不能因未达到建页门槛就丢失内容。

来源计数按独立来源家族计算：同一文档的 PDF/Markdown、复制件、转载通常计为一个来源；同一来源的修订版本不机械计为两个来源。质量优先于数量，两篇文章提到一个术语不代表它们支持完全相同的观点。

别名合并采用“标准标识 → 类型与版本 → 定义及上下文 → 相似度候选”的顺序。相似度不直接触发合并。不同模型版本保留独立 ID；缩写歧义、同名异义进入待复核列表。页面改名不改变实体 ID。

## 5. 加入本体后的 Ingest / Query / Lint

### 5.1 Ingest：证据先于页面

```text
用户放入原始资料
→ 监听/启动补扫，等待文件写入稳定
→ 哈希去重与来源版本识别
→ 解析正文、图片、表格或字幕并保留定位
→ 抽取候选实体、属性、关系、条件及证据
→ 别名归一与实体消歧
→ 本体类型、关系、来源和约束检查
→ 接纳有效断言，隔离无证据或不合法候选
→ 执行显式推理并保存依赖
→ 更新摘要、符合门槛的概念、对比和相关页面
→ 校验正文、断言、双链和索引一致性
→ 发布同一修订批次并写入日志
```

原始资料里的命令仅视为资料内容。抽取器没有写 raw、改规则或执行任意脚本的能力。LLM 产出候选；程序校验结构、权限、引用存在性和约束；证据是否真正支持陈述还需语义核对和抽样验收。结构校验通过不等于事实已经被证明。

解析失败、语义冲突或本体未覆盖的关系分别记录，不应导致有效原始资料丢失。自动任务需要可取消、可重试和明确错误展示。

### 5.2 Query：索引＋语义关系＋原始证据

每次先读取 CLAUDE.md、规则版本和 index.md。先从索引确定主题范围，再识别问题涉及的实体、版本、时间和关系。索引没有匹配条目时，可搜索候选记录与来源摘要；没有概念页不代表没有资料。

检索顺序：索引导航 → 相关 Wiki 页 → 受限的关系扩展 → 文本/向量补充召回 → 回到原文验证关键证据。图谱查询必须带当前用户、Vault、发布版本和证据状态过滤；只索引当前可访问资料。为关系扩展设置跳数和数量预算，避免全图注入模型。

回答明确区分：

1. **资料陈述**：原文直接支持，附具体引用。
2. **规则推导**：给出前提、规则与证据，标注为推导。
3. **未知或有争议**：说明证据缺口或不同条件下的分歧。

不因图中缺少边就断言“没有这种关系”。检索不可用、资料未处理、权限不允许、没有找到依据分别返回准确状态。证据不足时不得降级为自由聊天。该策略同时覆盖单模型和已有多模型协作链路。

入库条件：有可复用价值、关键事实有来源、无未标注争议、与既有内容去重且通过一致性检查。优先更新已有页面。保存的答案是派生内容，永不增加原始来源计数，也不能独立支撑后续推理。

### 5.3 Lint：结构、语义、证据、时效四类检查

| 检查 | 示例 | 自动处理边界 |
|---|---|---|
| 页面结构 | 断链、缺摘要、孤儿页、索引遗漏 | 目标唯一且语义明确时修复 |
| 本体约束 | 错误端点类型、非法关系、自我引用、禁止的环 | 拒绝发布违规记录或移入待复核 |
| 证据完整性 | 无来源断言、失效定位、生成答案充当原始证据 | 阻止进入可靠知识视图 |
| 语义冲突 | 同一版本、相同条件下的互斥陈述 | 核对原文；真实分歧保留双方 |
| 时间与版本 | 旧模型信息被用于新版本 | 标记适用范围与待核实状态 |
| 推理依赖 | 前提撤回、规则更新 | 使受影响推理失效并重算 |
| 概念门槛 | 有效独立来源数不足两份 | 标为候选/待复核并更新索引，不悄悄删除历史 |

每次摄入运行增量检查，每周执行完整检查。应用未运行时没有后台进程可执行的任务，应在下次启动补跑；若用户启用后台常驻，才按常驻计划运行。不凭内部语料声称已核验外部世界的最新状态。

## 6. 推理策略与标准选择

推荐首版使用轻量本体：版本化 YAML/JSON 定义＋TypeScript 校验与有限规则＋PostgreSQL 图投影。沿用现有数据库，先实现实体、边、证据与有限跳数查询；没有容量和查询证据前不引入独立图数据库。

推理仅运行明确批准的规则，例如类型继承、声明为互逆的关系。第一期禁止任意自然语言规则执行；不自动推导相关即因果、不自动传递“优于”“使用”“相关”。主题的 broader_than 不直接当成 subclass_of 推理。

每个推理结果记录 ruleId、ruleVersion、premiseAssertionIds 和 source lineage。推理循环需要去重与轮数/深度上限。任一前提失效后，该推理及依赖它的下游推理退出有效视图。

本体规则变更流程：建议 → 用户确认版本 → 计算受影响记录 → 暂存迁移及重算 → 校验 → 发布；失败保持旧版本可用，保留迁移记录。不要让一次修改关系含义静默改写全库。

标准参考与实现范围：

- OWL 用于理解类型、属性与逻辑语义。未知不能自动视为假；OWL 的语义推理与数据必填检查应分开。[W3C OWL 2 Primer](https://www.w3.org/TR/owl2-primer/)
- SHACL 用于 RDF 图的形状和约束验证。首版借鉴其约束方式，若未实现标准 RDF/SHACL 引擎，不宣称完全兼容 SHACL。[W3C SHACL](https://www.w3.org/TR/shacl/)
- SKOS 用于词表标签、别名及主题关系的设计参考；主题组织与逻辑类层次分别管理。[W3C SKOS Primer](https://www.w3.org/TR/skos-primer/)
- PROV-O 用于来源、派生与处理活动的设计参考。[W3C PROV-O](https://www.w3.org/TR/prov-o/)

首版选择的理由是与现有 TypeScript/PostgreSQL 工程匹配。完整 OWL 推理或外部本体互操作应在明确需要时再接入标准引擎；不能把自定义规则器称为完整 OWL 推理器。

## 7. 数据一致性、发布与恢复

每个 Vault 一个发布者。生成可并发，但写入必须排队。幂等键至少包含 Vault、来源 ID/哈希、流水线版本与本体版本。任务采用数据库持久队列与租约，避免与聊天任务争抢执行名额。

发布流程：记录基线哈希 → 暂存全部变化 → 检查文件路径、来源、关系、页面和索引 → 保存恢复日志 → 逐文件替换 → 校验完整批次 → 写完成标记 → 更新数据库投影到该修订。数据库更新失败可以重放投影，文件中断依恢复日志完成或回滚。

文件替换不等于整个目录的原子事务。AI-chat 阅读与问答只能使用已完成发布的同一 revision；发布期间使用上一完整快照。外部 Obsidian 可能短暂看到文件逐个更新，应缩短发布窗口并在日志显示处理中。

raw 的只读要求以目录 ACL/只读挂载及受限文件接口执行。维护进程不得继承现有上传服务对 raw 的写权限。最终应用的“添加资料”是用户明确发起的导入动作，由独立导入路径执行，不开放给 AI 自主调用；禁止覆盖同名原件，按新来源/版本保存。AI 建议的网络资料先展示，用户选择导入后才进入 raw。

删除来源由用户操作。AI 只撤销关联索引、标记受影响断言并重算，不能自行删除原件。备份应分别涵盖原始资料、规则与 Wiki、业务数据库；版本回滚不覆盖用户原始资料。凭据保留在既有安全存储，不写入 Vault。

## 8. 最终交付：一个统一应用

最终形态为 Windows 本地优先的 AI-chat 桌面应用：复用现有 Web 界面与服务，在统一桌面入口中提供所有用户功能。本阶段是正式验收项，不仅是把多个工具的链接放到同一页面。

统一导航：

| 页面 | 用户可完成的操作 |
|---|---|
| 工作台 | 查看待处理资料、任务状态、最近知识变化和待复核事项 |
| 资料库 | 用户导入、阅读原件、查看处理状态和原文定位 |
| Wiki | 阅读摘要/概念/对比/问答，浏览双链与反向链接 |
| 图谱 | 按类型、关系、时间、来源和状态筛选；点击边查看证据 |
| 问答 | 严格知识问答、证据面板、推理路径和自动沉淀记录 |
| 本体与规则 | 查看类型、别名、关系、约束、版本以及确认规则变更 |
| 维护中心 | Lint 报告、冲突处理、变更预览、恢复与回滚 |
| 设置与备份 | Vault 位置、模型、后台计划、成本上限、备份恢复 |

应用内阅读器支持 Markdown、[[链接]]、反向链接和附件引用。图谱至少提供“页面导航图”和“带类型的语义图”两个视图，并区分有证据的原文关系、推导关系和候选关系；来源与日志节点可筛除，避免淹没知识主题。

用户点击答案引用，可依次查看陈述、Wiki 页、原始证据。点击推导结论可展开前提和规则。不能只展示漂亮的连线而无法检查依据。

应用生命周期统一管理：一个安装/启动入口、初始化向导、服务健康检查、后台任务启停、升级迁移与备份。桌面外壳的具体框架在打包验证后选择，避免提前承诺现有 Next.js 服务可直接打成某种无依赖二进制。

现有 PostgreSQL、Redis、MinIO、模型服务可能继续作为内部进程或依赖存在；“一个应用”要求用户不必分别启动它们或在多个终端执行命令。安装器需要检测和引导依赖，模型下载可由用户选择并显示进度。新功能不得在一体化阶段遗留为必须手工执行的脚本。

Obsidian 是可选兼容入口。卸载或不安装 Obsidian，资料导入、知识阅读、图谱、问答、本体管理、维护和备份仍能完成。桌面应用是产品入口，文件格式保持开放和可迁移。

在既有仓库中新增或扩展以下模块；具体目录名为实施建议，当前未创建。

| 模块 | 职责 |
|---|---|
| packages/wiki | 页面、索引、日志、链接及批次发布 |
| packages/ontology | 类型/关系注册、实体归一、断言结构、约束与有限推理 |

## 10. 分期与验收

| 阶段 | 交付 | 验收结果 |
|---|---|---|
| P0 规则与样本 | 核心本体、页面规范、权限与来源策略、评测样本 | 相同问题的类型、证据、拒答规则可明确判定 |
| P1 知识编译闭环 | MD/TXT/文字型 PDF 摄入、来源摘要、候选实体、概念、索引、日志 | 两来源建概念、重复来源不重复计数，raw 哈希不变 |
| P2 本体驱动问答 | 关系检索、证据链、有限推理、严格回答与沉淀 | 能区分原文/推导/未知，回答沉淀不成为原始来源 |
| P3 自动维护与多模态 | 监听补扫、定期 Lint、冲突/版本/撤回传播、OCR、图片及字幕 | 中断可恢复，语义冲突有证据，多模态能定位 |
| P4 统一应用交付 | 全部页面、内置阅读与图谱、桌面入口、初始化、后台管理、升级备份 | 全部功能可从应用完成，Obsidian 可选，无手工脚本必经步骤 |

每阶段的功能从一开始通过 AI-chat 的统一权限与任务接口接入；P4 完成产品集成与交付，不到最后才拼接各自独立的数据和认证。

必须覆盖的验收场景：

1. 一份素材出现概念：保留候选与摘要，不发布独立概念页；第二份独立素材到来后晋升。
2. 同文不同格式、重复导入、转载与旧版本：不会虚增来源数量。
3. 两个同名实体和两个模型版本：不误合并；改名保持 ID 与引用有效。
4. 相同主题但不同条件的两个指标：保留条件，不直接判冲突或排名。
5. 无证据关系或非法端点类型：不能发布为可靠事实。
6. 图中缺失关系：回答未知，不能断言不存在。
7. 推理关系：展示前提、规则与来源；撤回前提后派生结论失效。
8. 单聊与多模型协作：无证据和检索失败均不会变成无依据回答。
9. 重复任务、双 worker、发布中断和数据库投影失败：无重复页面，可恢复完整 revision。
10. 跨用户、路径穿越与越权写入：被拒绝；AI 操作前后 raw 文件内容不变。
11. 修改本体版本：可查看影响、迁移和回退，不静默改变旧事实语义。
12. 图片/OCR/字幕质量不足：显示限制，来源定位真实，不伪造内容。
13. 退出并重开应用：资料和知识保留，必要后台任务恢复，遗漏定期任务补执行。
14. 不安装 Obsidian：可从同一应用完成导入、阅读、图谱、问答、维护和备份恢复。
15. 备份恢复：Wiki 和规则一致、引用可定位、业务数据可恢复；生成缓存可以重建。

语义抽取质量需要用用户实际领域样本评测，包含同义词、歧义词、矛盾资料、单来源事实、版本变化和完全无答案的问题。不能以模型自评或结构校验通过代替质量验收。先记录准确性、引用支持率、误合并、拒答与成本基线，再决定自动发布范围。

## 11. 可并入 CLAUDE.md 的新增规则草案

> 你是 AI-chat 内的知识维护助手，遵循本 Vault 的三层架构。每次任务先加载本文件、本体定义、约束、推理规则及其版本。
>
> raw 是用户管理的原始资料，你只能读取。所有解析、OCR、摘要、实体、关系、推理和问答结果写入 wiki。schema 与本规则文件的修改必须作为规则变更提交用户确认。
>
> 按本体抽取实体、属性、关系和证据。候选关系不等于事实。所有重要断言必须关联原始来源版本、定位和适用条件；不得把生成内容算作原始来源。
>
> 新领域概念至少由两份去重原始素材实质讨论后才建立正式概念页。首次出现保留候选与来源摘要，不能用实体页绕过门槛。系统预定义类型属于规则配置。
>
> 不凭相似名称或向量相似度合并实体。保留版本、别名和同名异义。[[链接]] 仅表示导航，不能替代经过证据核验的语义关系。
>
> 只执行已经批准的显式推理规则。推导结论必须标注，保留前提与规则版本；前提失效后撤销受影响结论。相关不能自动推成因果；未记录不能自动解释为不存在。
>
> 查询先读取 index.md，再按相关页面、语义关系和原始证据回答。区分资料陈述、规则推导、争议和未知。检索失败不得降级为无依据自由回答。
>
> 所有页面正文以一句话摘要开头，核心观点分点，标注来源；概念页包括定义、关联、应用与争议。对比页保留比较条件与资料缺口。答案通俗易懂，比喻须标为解释，不能充当证据。
>
> 满足来源、复用价值、去重和一致性条件的回答自动沉淀。它们是派生页面，不能增加原始来源计数或形成自证循环。
>
> 摄入与维护以可恢复批次发布，更新索引和只追加日志。结构错误可自动修复；真实分歧保留证据；不能自行编造事实以消除矛盾。外部新资料由用户决定导入。
>
> 所有知识操作应通过 AI-chat 统一接口完成，并保留开放 Markdown 及结构化数据。Obsidian 是可选阅读入口，不是完成任务的强制依赖。

## 12. 设计检查结论

- 保留了三层架构、raw 只读、两来源概念门槛、索引优先问答、引用与自动沉淀要求。
- 本体加入类型、实体消歧、带证据断言、约束、显式推理和版本治理，覆盖三个工作流。
- 单来源知识保留为候选与证据记录，不丢失、不绕过正式概念页门槛。
- 内容、结构化记录、规则和数据库投影的职责明确；跨文件发布不宣称全目录天然原子。
- 最终统一应用是必交付阶段，覆盖功能入口与运行管理；Obsidian 兼容性保留。
- 当前仅完成方案，没有修改 E 盘项目、创建 Vault、安装依赖、建立自动任务或验证运行效果。
